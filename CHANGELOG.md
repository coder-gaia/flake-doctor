## Main failure mode

An unattended tool-using agent needs two independent safeguards, and it is easy to build only the more interesting one. **Verification** (the four gates) judges whether the agent's *output* is correct, and it worked: Cheat Rate went from 21.4% to 0% across the three fixers, the cleanest result in this project. But nothing about verification constrains what the agent is *allowed to touch* while producing that output, and the very first unattended 14-case batch run demonstrated why that gap is not hypothetical: a tool-using fixer, given Bash/Read/Edit/Write and a working directory that happened to sit path-adjacent to the real benchmark fixtures, found and edited a checked-in original test file mid-run. Verification would have scored that run's *result* just fine; it was a `git status` check, not the oracle, that caught the problem. The fix (an OS-temp working directory with no structural link to the repo, plus an automated tracked-file diff that reverts and flags any change outside `results/`) is the unattended equivalent of ground rule 04's human-approval-before-a-consequential-action, and it only exists in this project because that specific incident forced it into existence, not because it was planned for in `dev-plan/PLAN.md`.

The second-place failure mode, smaller but real: a 120-second pytest-subprocess timeout on `shared_state_class_level_attribute` that consumed 1694 seconds of wall time and never reproduced on retry. `flakedoctor/eval.py` originally discarded a case's working directory before persisting anything if that case errored, so the first time this happened there was no artifact left to diagnose *why* the subprocess was slow. Fixed to persist on error too. The honest state of this one: still unexplained, and said so in the entry above rather than hand-waved.

## Hot take

Correctness and containment are two different problems, and an oracle that solves one does not touch the other. It is tempting to point at Verified Repair Rate or Cheat Rate and conclude the hard part of building a reliable agent is proving its output is right; this project's own incident log says otherwise. The verification loop was designed on paper before a single case ran and performed almost exactly as predicted. The sandbox escape was not designed for at all, it was discovered by accident, from a `git status` check run out of habit rather than as part of any planned gate, on the very first unattended multi-case run. If a real regression had been the only thing worth guarding against, this project would have shipped a benchmark that quietly corrupted its own ground truth while reporting a clean 92.9%. **The practical lesson for building agents with real tool access: budget as much deliberate engineering for "what is this agent allowed to touch" as for "how do I know its answer is right," because the second question is the one that gets designed on purpose and the first is the one that gets discovered the hard way.**
