# Improvement Changelog

Every meaningful iteration gets its own entry, tied to the evidence that motivated the next decision. Entries removed from the final design stay listed; what they taught us is part of the story.

| Stage | What we tried and why | Evidence | Decision / Learning |
|---|---|---|---|
| Benchmark construction | Built 14 synthetic flaky-test cases across 7 root-cause categories (timing, randomness, order dependence ×3, including a hard cross-file case, shared state, concurrency, environment, network), each seeded/controlled rather than dependent on raw wall-clock or hardware luck, so the benchmark itself reproduces across machines. | Every case run 40× as fresh `python -m pytest` subprocesses; flake rates recorded per `case.yaml` range 10%–70% (median ~35%). Full numbers in each case's `benchmark/cases/<id>/case.yaml`. | Kept all 14. Two design changes made *because* of this measurement pass, not before it (see below). |
| Design correction: mutant format | Originally planned `mutant.diff` (unified diff, per `dev-plan/PLAN.md`). | N/A (caught before writing any diffs, while reasoning through Windows CRLF line-ending behavior already visible in `git status` output on every commit so far). | Changed to a full mutated file under `mutant/src/<module>.py`, applied by overlay rather than `patch`/`git apply`. A diff's context-line matching is exactly the kind of thing CRLF/LF drift silently breaks; an overlay can't fail to apply. |
| Design correction: dict-mutation-during-iteration case dropped | Tried to make a case flake via Python's "dictionary changed size during iteration" `RuntimeError`, triggered by one thread deleting dict keys while another iterated it. | 0 crashes in 40 pytest runs, 0 in a 10-run direct stress test, 0 even after forcing `sys.setswitchinterval(0.0001)`. Diagnostic script showed the deleter thread was completing all deletions before the reader thread was ever scheduled once. | Replaced with `concurrency_duplicate_processing` (non-atomic check-then-act on a shared dedup set), the same jitter technique already proven on `concurrency_counter_race` (wide stagger before the critical section + narrow race window inside it), reused instead of re-deriving from scratch. Measured at 10% flake rate. |
| Detector requirement discovered mid-benchmark | While designing `order_dependence_singleton_reset`, realized its two tests fail *symmetrically* (exactly one always fails, whichever ran second), so the whole-run pytest exit code can't distinguish "flaky" from "reliably broken every run." | Naive exit-code measurement gave 40/40 fail; switching to checking the target test's own per-node result (`pytest -v` output for that node) gave the real 47.5% rate. | `flakedoctor/detect.py` reads a target test's specific outcome from a JUnit XML report, never the process exit code. Re-confirmed once built: exact 10.0% match on `timing_ttl_second_boundary`'s known rate, and the true ~50% (not a false 100%) on both symmetric-failure cases. |
| Oracle built: `detect.py` + `verify.py` | Built the four gates (stability, sensitivity, anti-cheat, blast-radius) before writing any agent code, per the plan, and validated each one against real cheat attempts rather than trusting the design on paper. | `tests/test_verify_harness.py`: a correct two-test fix for `timing_ttl_second_boundary` passes all four gates; three deliberate cheat variants (sleep-based masking, `@pytest.mark.skip`, a weakened assertion) are each caught. A skip marker also turned out to slip past a naive JUnit parse (pytest reports it as `<skipped>`, not `<failure>`) until `_parse_junit` was fixed to treat skipped as failed. | Kept the design. One real gap surfaced: `assert cache is not None` keeps the same assert count as the original assertion, so V3's counting heuristic alone lets it through; only V2's mutation test catches it. This is the first hard evidence for the project's hot take: semantic verification (V2) is load-bearing, static pattern-matching (V3) is a cheap complement, not a substitute. |
| Design correction: Tool Runner (raw API) → Claude Agent SDK | Planned architecture called for `client.beta.messages.tool_runner` against the raw Anthropic API, priced per token via `ANTHROPIC_API_KEY`. Turned out there was no budget for that: no separate Anthropic Console account, only an existing Claude Pro subscription with no spare spend intended for this project. | Live test: `claude_agent_sdk.query(prompt="...")` on this machine, with no `ANTHROPIC_API_KEY` set anywhere in the environment, returned a normal response. The session init message reports `apiKeySource: 'none'`; the accompanying `RateLimitEvent` reports `rate_limit_type: 'five_hour'` with utilization drawn from the Pro subscription's rate-limit window, not a billed API request. | Rebuilt the agent layer on the Claude Agent SDK instead of the raw Messages API. Same credential resolution order as the `claude` CLI itself (API key first, logged-in subscription session as fallback), so the exact same code runs unmodified for whoever reproduces this with a paid API key later and for this project's own zero-extra-cost development now. `flakedoctor/verify.py` needed zero changes: it never called an LLM in the first place. Narrow tool surface preserved via `ClaudeAgentOptions(allowed_tools=[...])` instead of hand-defined tool schemas. |

| Baseline B1 established | One direct prompt containing only the flaky test file's content (no source code, no tools, no execution), matching the challenge brief's own suggested minimal baseline. Deliberately the least capable thing that could work, so any later improvement has to trace to a specific design choice, not a bigger model (B1 and the final agent use the same `claude-sonnet-5`). | Canonical run: **9/14 cases (64.3%) reach Verified Repair Rate**. Full per-case gates in `results/b1_baseline.json`; the actual fixed files B1 wrote are kept in `results/candidates/b1_baseline/`, not just pass/fail booleans, and every claim below is read from those checked-in files. One structural pattern explains 3 of the 4 `sensitivity` failures: `order_dependence_cross_file`, `order_dependence_fixture_leak`, and `shared_state_mutable_default_arg` each get a real, working fix for the flakiness itself (a fresh-`uuid` user id per call, a function-scoped fixture, explicit fresh lists instead of the shared default) without ever re-exercising the exact behavior each case's mutant breaks: the VIP-discount branch stays untested because the fix routes around VIP users entirely, and both duplicate-check mutants go uncaught because none of B1's own test calls happen to pass the *same* item twice. The fourth, `shared_state_class_level_attribute`, is sharper: B1 is never shown `src/cart.py` (the prompt is test-file-only, by design), so it cannot touch the actual class-level-attribute bug; it wrote its own new test, `test_carts_do_not_share_items_within_a_test`, that correctly proves the fix incomplete (`assert second.total() == 0.0` fails with `19.98`), but never ran it to find out. `network_simulated_timeout` is a near-miss rather than a miss: B1 added the always-failing-client test `case.yaml` names as "the right fix," but asserted `2 <= calls <= 4` instead of `calls == 3`, a boundary loose enough that the off-by-one mutant's 2 calls satisfy it anyway. | Kept B1's design unchanged; this blindness is the honest baseline, not a bug to route around. Every failure above is a mistake B1 never got to see, because it never reads the production source and never executes anything. That is the cleanest evidence yet for why the final agent's tool access (read the real code, run pytest before finalizing) and the verification loop should matter, not an assumed benefit. |
| Design correction: fixers must keep the target test's exact name | Two early runs reported `stability: False` for `random_unseeded_sampling`, which looked like B1 had left it flaky. | Rerunning `detect.py` directly against the persisted candidate showed 0/30 failures once matched by the function name B1 actually used. B1 had renamed `test_heavily_weighted_item_is_picked_first` to the more descriptive `test_heavily_weighted_item_dominates_the_draw`, which nothing in the prompt forbade. Grepping all 14 persisted candidates for the original name confirmed this was the only case affected. | Added an explicit line to the prompt template: the target function "must keep its exact name." Hardened `verify_stability` to report "target test not found in any run" as its own distinct failure reason instead of silently reading as 100% flaky, the same class of measurement bug the JUnit-`skipped` fix caught earlier. Re-ran the full 14-case suite as the canonical result. Honest residual finding, not hidden: `network_simulated_timeout`, `shared_state_class_level_attribute`, and `timing_daily_window_boundary`/`timing_ttl_second_boundary` flip verdict across otherwise-identical reruns from ordinary LLM output variance, while `order_dependence_cross_file`, `order_dependence_fixture_leak`, and `shared_state_mutable_default_arg` fail on every single run. The reproduction guide will report the canonical run plus this observed variance, not whichever number looks best. |

| Agent v1 (B2) built, single-case smoke test | Built the tool-using fixer (`flakedoctor/agent.py`, `ClaudeSDKClient`, `tools=["Read","Grep","Glob","Edit","Write","Bash"]`, same model as B1). Ran it alone on the hard case first, `order_dependence_cross_file`, before committing to a full 14-case batch. | Genuinely strong trajectory: unprompted, it read both `tests/test_billing.py` and `tests/test_auth.py`, ran the suite across explicit `--randomly-seed` values to reproduce the failure before touching anything (seeds 1 and 2 failed, confirmed), diagnosed the shared `_SESSIONS` dict correctly, added a real `reset_sessions()`/`logout()` API to `src/auth.py` plus an autouse fixture, and reverified across 12 seeds plus 5 more random runs, all green, before stopping. 14 turns, $0.087 notional. | This is real root-cause repair, not a workaround, the opposite of every B1 failure pattern in the row above. Confidence high enough to launch the full 14-case batch next. |
| Critical fix: tool-using fixers were not actually sandboxed | Launched the full 14-case B2 batch with each case's live candidate persisted directly under `results/candidates/b2_agent_no_verification/<case>/`, the same layout that worked safely for B1. | Mid-run, `git status` showed `benchmark/cases/environment_decimal_context_leak/tests/test_pricing.py`, the checked-in original fixture, modified. B1 could never have done this (`tools=[]`, no tool access at all); B2 has Bash/Read/Edit/Write with no path restriction beyond `cwd`. Persisting the live workspace at `results/candidates/<label>/<case_name>/` put it path-adjacent to the real `benchmark/cases/<case_name>/`, and the agent found and edited it. `ClaudeAgentOptions.sandbox` (Bash-level OS sandboxing) turned out to be macOS/Linux only per its own docstring, not available on this Windows dev machine; the documented alternative is Read/Edit permission deny-rules, which real enforcement wasn't built out under the hackathon clock. Damage was contained to that one file and reverted with `git checkout --`; confirmed via full `git status` that nothing else was touched. | Stopped the batch immediately rather than let it keep running. Three changes, not one: (1) a fixer's live workspace is now always a real OS temp directory with no structural link back to the repo, regardless of whether results get persisted; a snapshot copy is taken into `results/` only after the fixer finishes. (2) Added an automated integrity check around every case in `flakedoctor/eval.py`: tracked-file diff before and after, any change outside `results/` is reverted immediately and the case is marked `SANDBOX_VIOLATION` instead of trusted. This is the automated, unattended stand-in for ground rule 04's "human approval before a consequential action" when a batch runs unattended across many cases. (3) Hardened the agent's own system prompt with an explicit boundary instruction, as defense in depth on top of the structural fix, not a replacement for it. Leading candidate for this project's hot take: giving a tool-using agent shell access without real OS-level sandboxing is a genuine gap, observed empirically on the very first unattended batch run, not a hypothetical one. |

The user was explicit from the start of this project that no additional spend is acceptable (`dev-plan/PLAN.md`'s Claude Agent SDK correction exists because of exactly that constraint); running past a hard limit is one thing, silently crossing into billed usage is another. Full 14-case B2 run resumes once the account setting is confirmed off or the window resets. |
